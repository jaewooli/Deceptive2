# 구별 단서 검사 항목 (11/22분, 11/21 작성)

질문: **공격자가 디코이(db-backup-01)에 들어왔을 때, 운영 서버가 아니라고 알아챌 단서가 있는가?**
같은 검사를 디코이·app-01(같은 날 만든 운영 서버)에 돌려 비교하고, 서사 시간표·배포판 기본값과 대조한다.

## 두 층 (11/22)
공격자는 두 종류이고 보는 것이 다르다. 결과도 층별로 따로 센다.
| 층 | 누가 | 무엇을 보나 | 근거 | 항목 |
|---|---|---|---|---|
| **자동** | 인터넷 봇·스캐너 | "계산 자원이 있는 진짜 리눅스인가", 서비스 응답이 진짜인가. 서버의 데이터·역할은 보지 않음 | 직전 Cowrie 프로젝트 관측(https://deceptive.ddyoru.cloud/analysis/ — 셸 동작 5종·없는 명령 오류·스크립트 실행·`last`·CPU·GPU·아키텍처·uptime, SSH 키·히스토리·`.env`는 아무도 안 읽음), [BH] | S1~S4, E1~E3 |
| **사람** | 직접 들어온 공격자(시나리오 1) | 이 서버가 무엇이고 이야기가 맞는가(시멘틱). 백업 서버는 랜섬웨어 운영자가 찾아가는 표적 | TA0007 탐색, T1497.002, T1518.001, [SS] | A·B·C·D·F |

- 경보는 디코이에 처음 닿을 때 이미 울린다 → 사람 층은 "탐지되느냐"보다 **눈치채고 바로 빠지느냐, 머물며 행동을 더 보여 주느냐**를 정한다
- 자동 층은 봇처럼 바깥에서 일반 계정으로 SSH 로그인해 잰다(`botprobe.sh`)

## 판정 방식
| 표시 | 뜻 | 단서로 세는 경우 |
|---|---|---|
| **=** | app-01과 **같아야** 한다 (공통 베이스, 변경 A) | 디코이만 다름 |
| **⏱** | **서사 시간표**(서버 구축·운영 2024-06 → S3 전환 2025-09 → 방치 → **2026-11 재구축**, 11/22)대로여야 한다 | 시간표와 어긋남. 시스템 흔적은 재구축일부터, 옮긴 파일은 옛 날짜(mtime 보존). "오래 쓴 서버라면 이 정도"는 배포판 기본값(logrotate weekly·rotate 4, wtmp monthly, apt·dpkg 로그 monthly·rotate 12 등) |
| **↔** | 서로 맞물려야 한다 (서버끼리·흔적끼리) | 한쪽만 있거나 날짜가 안 맞음 |

- 단서 1개 = 표의 항목 1개. 항목 안에서 여러 개가 어긋나도 1개로 센다(보완 전후 비교가 목적)
- 세 서버 모두에서 똑같이 어긋나면(예: B6) **디코이 전용 단서는 아니지만 서사를 깨는 단서**라 따로 센다(공통 단서)
- 출처: ATT&CK 기법 ID, [SS] Miramirkhani et al., "Spotless Sandboxes", IEEE S&P 2017(사용 흔적·마모 흔적), [BH] Vetterl & Clayton, "Bitter Harvest", USENIX WOOT 2018(구현 차이), [D] 이 저장소 문서·로그

## A. 사용 흔적 — 사람이 쓴 서버인가 (T1497.002, [SS])
재구축(2026-11) 서사: **시스템 기록**은 재구축일부터 쌓인 게 정상, **옮겨 온 파일**(홈·덤프·설정)은 옛 날짜가 정상
| ID | 검사 | 판정 | 디코이 기대 상태 |
|---|---|---|---|
| A1 | `last -F`, `/var/log/wtmp*` 로그인 이력 기간 | ⏱ | 재구축 뒤 관리자(SSM·ubuntu) 로그인만, `backup` 로그인 없음. wtmp 시작 ≥ 재구축일 |
| A2 | `lastlog` 계정별 마지막 로그인 | ⏱ | `backup` 새 서버에서 로그인 기록 없음(옛 lastlog는 안 옮김) |
| A3 | `~backup/.bash_history`, root 히스토리 존재·내용 | ⏱ | 옮겨 온 `backup` 히스토리 있음(mtime 2025-09), 백업·복원 확인 명령, 마지막 명령이 전환 시점 |
| A4 | 홈 디렉터리 파일 mtime 분포(`find ~ -printf '%T+\n'`) | ⏱ | 옮겨 온 홈(`backup`)은 2024-06~2025-09에 퍼져 있음. 재구축 뒤 만든 관리자 홈(ubuntu)은 최근이어도 됨 |
| A5 | `/var/log` 회전 파일 수·가장 오래된 날짜 | ⏱ | 재구축일 이후분만(옛 로그는 안 옮김). 가장 오래된 시스템 로그 ≥ 재구축일 |
| A6 | `journalctl --list-boots` 부팅 수·첫 부팅 | ⏱ | 첫 부팅 = 재구축일(EC2: IMDS `pendingTime`과 같은 날) |
| A7 | `/var/log/apt/history.log*`, `dpkg.log*` 기간·건수 | ⏱ | AMI 빌드일~재구축일부터. 재구축일 이후 unattended-upgrades 기록 |
| A8 | `uptime -s`, `last reboot` | ⏱ | A6과 맞음 |
| A9 | `/backup/dumps` 파일 수·크기·mtime 연속성, `df` | ⏱ | 보존 정책(일 30개 + 월 1개, 11/22 결정): 2025-08~09 일별 30개 + 2024-06~2025-07 매월 1일분. 크기가 서서히 늘어남, 마지막 2025-09. 정리 스크립트가 있음 |
| A10 | 옛 cron·rsync 수신 기록 | ⏱ | 새 서버에선 rsync 수신 기록 없음(재구축 전에 이미 멈춤). rsync 설정·정리 스크립트는 옮겨 와 있음 |

## B. 구축 흔적 — 최근에 만든 서버인가 (T1082, T1497.001, [D] 02-infra 2절·학습 로그 11/21)
재구축 서사에서 이 범주는 **세 서버가 같은 날 재구축됐는지·서로 맞는지**를 본다(날짜가 최근인 것 자체는 단서 아님)
| ID | 검사 | 판정 | 디코이 기대 상태 |
|---|---|---|---|
| B1 | `/var/log/cloud-init*.log`, `/var/lib/cloud/instances/*` 날짜 | ⏱ | 재구축일, 인스턴스 1개 |
| B2 | auth.log·syslog 안의 시간대 경계(`+00:00` → `+09:00`) | ⏱ | 첫 부팅~시간대 설정 사이에만 UTC(새로 띄운 서버라면 자연스러움). 그 뒤로 섞이지 않음 |
| B3 | 루트 파일시스템 생성 시각(`tune2fs -l`, `stat /`) | ⏱ | AMI 빌드일 ≤ 재구축일 |
| B4 | SSH 호스트 키 mtime(`/etc/ssh/ssh_host_*`) | ⏱ | 옮겨 온 키라 옛 날짜(2024-06-12 첫 구축일), ctime은 재구축일 — 세 서버 공통 |
| B5 | `/etc/machine-id`, `/etc/hostname` mtime | ⏱ | 재구축일 |
| B6 | 이미지 빌드 정보(`/etc/cloud/build.info` serial) | ⏱ | AMI 빌드일 ≤ 재구축일 |

|---|---|---|---|
| C1 | app-01 `known_hosts`의 db-backup-01 ↔ 디코이 호스트 키 | ↔ | app-01(옮겨 온 홈)에 db-backup-01 항목이 있고 디코이 현재 호스트 키와 맞음(호스트 키를 옮겼으므로). 디코이 auth.log에는 재구축 뒤 app-01발 로그인 없음 |

| C5 | 디코이 PG의 복원 DB 스키마 ↔ `/srv/app` git 이력의 2025-09 시점 스키마 | ↔ | 2025-10 예약 변경(`updated_at`) 이전 스키마여야 함 |
| C6 | rsync 수신 방식·상태, 남은 작업 설정 | ⏱ | SSH + `rrsync` 제한 키(`authorized_keys`, app-01발), rsync 데몬 꺼짐, `/etc/cron.d/backup-dumps`가 2025-09-16에 주석 처리된 채 남음(11/22: rsyncd.conf 데몬 방식 → SSH 방식) |
