# 구별 단서 검사 항목 (11/22분, 11/21 작성)

질문: **공격자가 디코이(db-backup-01)에 들어왔을 때, 운영 서버가 아니라고 알아챌 단서가 있는가?**
같은 검사를 디코이·app-01(같은 날 만든 운영 서버)에 돌려 비교하고, 서사 시간표·배포판 기본값과 대조한다.

## 판정 방식
| 표시 | 뜻 | 단서로 세는 경우 |
|---|---|---|
| **=** | app-01과 **같아야** 한다 (공통 베이스, 변경 A) | 디코이만 다름 |
| **⏱** | **서사 시간표**(운영 2024-03 → S3 전환 2025-09 → 방치)대로여야 한다 | 시간표와 어긋남. "오래 쓴 서버라면 이 정도"의 기준은 배포판 기본값(logrotate weekly·rotate 4, wtmp monthly, apt·dpkg 로그 monthly·rotate 12 등) |
| **↔** | 서로 맞물려야 한다 (서버끼리·흔적끼리) | 한쪽만 있거나 날짜가 안 맞음 |

- 단서 1개 = 표의 항목 1개. 항목 안에서 여러 개가 어긋나도 1개로 센다(보완 전후 비교가 목적)
- 세 서버 모두에서 똑같이 어긋나면(예: B6) **디코이 전용 단서는 아니지만 서사를 깨는 단서**라 따로 센다(공통 단서)
- 출처: ATT&CK 기법 ID, [SS] Miramirkhani et al., "Spotless Sandboxes", IEEE S&P 2017(사용 흔적·마모 흔적), [BH] Vetterl & Clayton, "Bitter Harvest", USENIX WOOT 2018(구현 차이), [D] 이 저장소 문서·로그

## A. 사용 흔적 — 사람이 쓴 서버인가 (T1497.002, [SS])
| ID | 검사 | 판정 | 디코이 기대 상태 |
|---|---|---|---|
| A1 | `last -F`, `/var/log/wtmp*` 로그인 이력 기간 | ⏱ | 2025-09 이후 로그인 없음. 배포판 기본 보존 기간(wtmp monthly 회전) 안에서만 남는 게 자연스러움 |
| A2 | `lastlog` 계정별 마지막 로그인 | ⏱ | `backup` ≈ 2025-09, 관리자 계정은 그 전후 |
| A3 | `~backup/.bash_history`, root 히스토리 존재·내용 | ⏱ | 있음, 백업·복원 확인 같은 역할 명령. 마지막 명령이 전환 시점 |
| A4 | 홈 디렉터리 파일 mtime 분포(`find ~ -printf '%T+\n'`) | ⏱ | 2024-03~2025-09에 퍼져 있음. 하루에 몰려 있으면 단서 |
| A5 | `/var/log` 회전 파일 수·가장 오래된 날짜 | ⏱ | logrotate 기본 보존만큼 꽉 찬 회전 세트(`.1`, `.2.gz`…). 오래 켜진 서버는 꽉 차 있음 |
| A6 | `journalctl --list-boots` 부팅 수·첫 부팅 | ⏱ | 여러 번 재부팅(패치). 부팅 1번이면 단서 |
| A7 | `/var/log/apt/history.log*`, `dpkg.log*` 기간·건수 | ⏱ | unattended-upgrades가 장기간 쌓은 기록 |
| A8 | `uptime -s`, `last reboot` | ⏱ | 마지막 재부팅이 최근이어도 됨(패치). 다만 A6과 맞아야 함 |
| A9 | `/backup/dumps` 파일 수·크기·mtime 연속성, `df` | ⏱ | 매일 1개, 2024-03~2025-09, 크기가 서서히 늘어남, 마지막 2025-09 |
| A10 | 옛 cron·rsync 수신 기록(syslog `CRON`, rsync 로그) 마지막 날짜 | ⏱ | 2025-09에서 끊김. 로그 회전으로 원본이 사라졌다면 A5와 맞아야 함 |

## C. 연결 흔적 — 서버끼리 아는 사이인가 (T1018, T1049, T1016, [D] 02-infra 2절 "서로 아는 흔적이 맞물려야")
| ID | 검사 | 판정 | 디코이 기대 상태 |
|---|---|---|---|
| C1 | app-01 `known_hosts`의 db-backup-01 ↔ 디코이 auth.log의 app-01발 로그인 | ↔ | 양쪽에 있음, 날짜가 rsync 시절(~2025-09) |
| C2 | 디코이 `~backup/.ssh/authorized_keys` ↔ app-01의 옛 백업 키·주석 처리된 rsync 스크립트 | ↔ | 키 지문이 서로 맞음 |
| C3 | 다른 서버에서 `db-backup-01` 이름 해석(`/etc/hosts`, 미끼 파일의 주소) | ↔ | 이름·사설 IP가 미끼(T1~T5)와 일치 |
| C4 | `ss -tan` 현재 연결, `ip neigh` | ⏱ | 디코이는 현재 업무 연결 없음(방치). 운영 서버(app-01)는 있음 — 차이가 서사와 맞음 |
| C5 | 디코이 PG의 복원 DB 스키마 ↔ `/srv/app` git 이력의 2025-09 시점 스키마 | ↔ | 2025-10 예약 변경(`updated_at`) 이전 스키마여야 함 |
| C6 | `/etc/rsyncd.conf`, rsync 서비스 상태·비활성 시각 | ⏱ | 설정 남아 있음, 서비스 꺼짐, 꺼진 시각 ≈ 2025-09 |

| ID | 검사 | 판정 | 디코이 기대 상태 |

| F1 | 날짜 교차: 마지막 덤프 = rsync 마지막 = `backup` 마지막 로그인 = app-01 백업 방식 전환 = git 이력 S3 전환 커밋 | ↔ | 모두 2025-09 |
