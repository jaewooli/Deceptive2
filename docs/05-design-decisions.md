# 설정 요소별 고민과 선택 (11/19~11/23)

이 프로젝트(Deceptive-2)는 시중 디셉션 기술을 벤더 메커니즘대로 직접 구현하고, 공격자 앞에서 먹히는지 검증한다.
아래는 그 과정에서 정한 모든 설정을 **요소별로** 묶은 것이다. 각 요소는 `고민(대안)` → `선택` → `근거` 순서이고, 날짜는 결정한 날이다.
자세한 경위는 `docs/04-learning-log.md`(막힌 점·깨달음), `docs/plan-wbs.md` 8절(진행 기록), `docs/HANDOFF.md`(현재 상태)에 있다.

**모든 결정을 관통하는 세 가지 기준**
1. **진짜 서버와 구별되지 않을 것** — 디코이에만 있는 것(감시 흔적·설정·하드웨어 값)은 단서다. 판단은 "같은 환경의 진짜 서버와 같은가"로 잰다
2. **벤더 메커니즘대로, 줄일 땐 묻는다** — 문서의 축소안도 벤더 원문(특허·데이터시트)과 대조한 뒤 결정. 비용은 판단 근거가 아니다(11/21)
3. **디코이 장치가 망가져도 운영은 멀쩡할 것(fail-safe)** — 운영 서버를 디코이로 쓰는 순간 디코이 장애 = 운영 장애(11/22)

## 2. 네트워크
- **서브넷**: VPC 10.0.0.0/16 — public 10.0.1.0/24(web-01), internal 10.0.2.0/24(app-01·db-backup-01), farm 10.0.3.0/24(투영 팜, 11/22)
- **내부 서버의 바깥 통신**
  - 고민: NAT 게이트웨이(실제 회사 구조) / 공인 IPv4 + 인바운드 전면 차단
  - 선택: **공인 IPv4 + 보안 그룹으로 인바운드 차단**, NAT 금지(CLAUDE.md 규칙)
  - 한계(기록): 실제 회사라면 NAT를 쓴다
- **관리 접속**: SSH 대신 **SSM Session Manager** — 관리용 포트가 열려 있으면 그것도 단서·공격면
- **S3 접근**: S3 게이트웨이 엔드포인트(내부 서버가 인터넷 없이 백업)
- **경보 경로**: web-01 경유 제외 — 시나리오상 가장 먼저 장악되는 호스트
- **MTU**: VPC 안은 9001. 터널을 거치는 디코이도 이웃과 같은 MTU여야 함(5·9절)
- **로컬 랩의 구간**(11/23): 처음엔 LAN 하나 → web-01 ARP에 팜이 보이는 로컬 전용 한계 → **LAN 2개(int·pub) + 라우터 VM**. AWS VPC 라우터는 서브넷 사이에서 TTL을 안 줄이므로 로컬 라우터도 TTL을 되돌림

## 3. 방화벽(보안 그룹·호스트 규칙)
| 대상 | 인바운드 | 왜 |
|---|---|---|
| web-01 | 80/443 ← **내 공인 IP만** | 의도적 RCE가 있는 호스트를 인터넷에 열지 않음. 공개 노출 실험(12/2~) 때만 개방 — 한계로 기록 |
| app-01 | 22, 5432 ← 10.0.0.0/16 | 웹 → 내부 DB는 실제 회사처럼 허용 |
| db-backup-01 | 전체 ← 10.0.0.0/16 | 정상 업무에서 아무도 안 쓰는 서버 → **접속 자체가 신호** |
| sensor 관리 ENI | 없음(SSM) | 스캔에선 열린 포트 없는 주소 |
| sensor 투영 ENI | 전체 ← 10.0.0.0/16 | 투영 디코이 주소 — db-backup-01과 같은 원칙 |
| farm | UDP 51820 ← sensor, 51821~ ← EDH | 회사 망에서 팜으로 직접 오는 길 없음 |
| EDH 디코이 포트 | web-01 8080, app-01 6379 ← 10.0.0.0/16 | 운영 서버의 안 쓰는 포트 → 팜 트랩(규칙이 고른 포트, 레지스트리 기준) |
- **호스트 쪽 규칙 원칙**(11/22~23): 디코이 장치가 거는 규칙은 **자기 테이블·체인·경로표만**(nft `local_fwd`·`local_gate`·`edh_N`, iptables `LOCAL_FWD`, 경로표 110~·120·141~·191~). 운영 서버의 local 규칙(pref 0)은 절대 안 옮김(11/22 먹통 사고), networkd 외래 규칙 보존 설정
- **기능을 끌 때 규칙도 지운다**(11/23): 끈 감시가 남긴 TPROXY·DNAT 규칙이 디코이 PG를 막거나 포트를 계속 넘겼다 → 시작할 때 정리, 단 **우리 흔적이 있을 때만**(남의 경로표를 비우지 않게)
- **WSL2 팜**: Docker가 있으면 FORWARD 기본 DROP일 수 있음 → 팜 인터페이스끼리만 허용(DOCKER-USER)

## 5. auditd
- 고민: 디코이에만 촘촘한 감사 규칙 / 모든 서버에 같은 규칙
- 선택: **세 서버 공통 — 배포판 예제(10-base-config + 30-stig + 43-module-load) + 로그인 세션 execve(`auid!=unset`), 99-finalize 없음**(11/20). 30-stig의 NetworkManager 규칙은 없는 서버에서 로드 오류 → `12-ignore-error`로 그 줄만 건너뜀
- 근거: 디코이에만 있는 규칙은 단서. 로그인 세션 명령 기록은 공격자 세션 수집(벤더 "디코이 행동 기록")의 바탕
- **디코이 빌드와의 충돌**(11/23): 원격 명령으로 디코이를 만들면 디코이 자신의 감사 로그에 `touch -d 2024-…` 같은 빌드 명령이 남음 → 디코이 세팅은 **로그인 세션이 아닌 cloud-init**(auid 없음)과 **꺼진 디스크**에서만. 결과: 감사 규칙 전체가 진짜 서버와 md5까지 같음
- 한계: 컨테이너 디코이는 auditd 불가(11/22 D4) → VM으로 전환한 이유 중 하나
- **미끼 열람·결과 기반 감시(11/23, 원래 11/26)**
  - 고민: 미끼 파일마다 정확한 규칙(오탐 적음) / **자격증명 위치 일반 규칙**(모든 서버 같은 모양)
  - 선택: **일반 규칙** — 로그인 셸 계정의 `~/.ssh`·`~/.aws` 안 파일 열람, 서비스 필수 `EnvironmentFile` 열람(`secret-files`) + `authorized_keys`·`~/.ssh` 만들기·`/etc/ld.so.preload`·`/etc/cron.d`·사용자 crontab 변경(`persistence`, crontab은 사용자 추가). 계정이 서버마다 달라 규칙은 그 서버 계정에서 생성(`audit/account-rules.sh`, 꺼진 디코이 디스크도)
  - 근거: 미끼마다 규칙을 두면 root를 딴 공격자가 `auditctl -l` 한 줄로 미끼 위치를 안다 — Illusive가 엔드포인트에 감시를 두지 않는 이유와 같은 문제. 일반 규칙이면 미끼가 지목되지 않고 진짜 자격증명 탐색도 잡힘
  - 대가: 진짜 파일 열람도 경보 → 11/30. 첫 실측: SSM 에이전트가 `/root/.aws/credentials`를 약 30초마다 읽음(로컬 랩 전용 파일 — EC2 11/28 확인), ssh가 `~/.ssh/config`·키를 읽음
  - 알게 된 것: `exe!=`는 `auditctl -l`에 `exe=`로 보임(반대 뜻으로 읽힘) → 거르기는 데몬에서. `auditctl -l`은 path·dir 규칙을 `-w` 형식으로 보여 줌

- **서버에 올라가는 코드·이름에 프로젝트 용어 금지**(경보 데몬 이름도 회사 도구처럼 `moa-notify`)

## 8. 디코이 db-backup-01(깊이 — 자체 설계, 항상 켬)
- **5432 서비스**
  - 고민: 파이썬 더미 리스너 / 진짜 PostgreSQL
  - 선택: **진짜 PostgreSQL 16 + `log_connections`**(11/20) — 흉내 낸 프로토콜의 응답 차이 단서(Vetterl & Clayton 2018)와 "디코이 전용 프로세스" 단서가 함께 사라짐. 같은 로그 설정을 app-01에도(CIS 권고)
  - 미끼 DB 계정은 만들지 않음 → 로그인은 실패하고 로그에 남음. 경보는 **모든 접속**. 서버에 미끼 이름 목록을 두지 않음(공격자가 읽을 수 있으므로)
- **옮겨 온 데이터**(11/22): `backup` 계정·히스토리·덤프 45개(최근 30 + 매월 첫, PG 버전·`\restrict`를 Launchpad 배포 이력대로)·rrsync 키·복원 DB·주석 처리된 cron. 사용 흔적은 S3 전환 시점까지만 쌓이고 멈춘 모습
- **IP**: 다중 주소(보조 IP 3개) → 투영으로 바꾸며 **IP 1개**(11/22)
- **분류**(11/23): "진짜 OS로 만든 고상호작용 디코이"는 특정 벤더 기술이 아님 → 벤더 스위치 대상에서 빼고 항상 켬

## 9. 미끼(Illusive 맥락 기반 배포, US10382483)
- **함정 T1~T6**: T1 `.env`의 꺼진 기능 DB URL, T2 ssh config + 미끼 키, T3 bash 히스토리(T2로 유도), T4 잊힌 tmux 세션의 ssh-agent 키(메모리에만), T5 대기 중 동기화 서비스의 환경변수, T6 `~/.aws/credentials [backup-legacy]`. T7(공개 `.env`)은 12/2 이후 실험
- **배치 방식**
  - 고민: 미리 정한 위치에 손으로 / 서버 맥락을 보고 규칙으로
  - 선택: **맥락 기반 엔진**(`baits/`, 11/22) — 수집(값은 안 읽음) → 규칙(유형 8개) → 적용(표시 없음·시각 보존) → 검증(드리프트 = 경보 + 복구) → 교체(옛 ID는 retired로 남겨 계속 감시) → 회수. 레지스트리로 관리, 배포는 손이 아닌 Ansible/SSM(변경 C)
  - 근거: 벤더 원문(맥락에 맞는 미끼가 진짜처럼 보임). 미끼는 **진짜로 쓰인 서버**에서만 성립 → web-01 deploy 흔적·git 이력·app-01 PG 실제 연결을 먼저 만듦
- **제약**: app-01 postgres의 옛 rsync 개인키는 S3 전환 때 지웠다(사용자 결정) → T1~T6 밖의 새 미끼를 만들지 않음
- **비밀값**: 미끼 실제 값은 저장소에 넣지 않고 배포 때 주입. 레지스트리는 로컬(커밋 안 함), AWS에선 비공개 S3 예정

## 10. 트랩 서버 중계(Illusive, US10404747)
- 운영 서버(EDH)의 **안 쓰는 포트** → 터널 → 팜의 트랩(그 서버의 주소·hostname을 가진 진짜 Redis/nginx). 역할 규칙: DB 서버 → Redis 6379, 웹 서버 → 관리 8080
- **주소 변환**
  - 고민: masquerade / 주소 그대로
  - 선택: **주소 변환 없는 이중 DNAT**(11/22) — masquerade하니 Redis `CLIENT LIST`가 `addr=EDH 자신`·`laddr=트랩 내부`를 보여 중계가 드러남. 서비스는 자기·상대 주소를 말한다
  - 정책 규칙(ip rule)은 운영 서버에 쓰지 않음 — local 규칙을 옮겼다가 networkd 재시작에 운영 서버가 먹통(11/22)
- **양보**: 실제 프로그램이 그 포트를 쓰기 시작하면 넘기기를 멈춤(특허의 충돌 회피). 1초 주기 확인 — bind 순간을 잡는 벤더 에이전트보다 1초 틈이 남음(한계)
- **cache_hint**: 활성 트랩 포트만 가리키는 미끼(같은 특허)
- **L3 단서 제거**(11/23): 같은 서버인데 22번은 TTL 64, 넘긴 포트는 62 → 포워딩 홉마다 TTL +1(양방향)

## 11. 연결 테이블 미끼(Attivo, US10375110 — 벤더 문서의 Illusive 귀속을 정정)
- 공격자는 `netstat`·`ss`·`ip neigh`로 다음 표적을 고름 → T5 report-sync가 디코이 5432에 **핸드셰이크만 한 연결**을 무작위 간격으로 유지
- **오탐 문제**: 미끼 연결도 공격자도 같은 web-01에서 옴 → 출발지로 못 가름 → 벤더처럼 **페이로드로 가름**: 디코이 앞 투명 관문(TPROXY) — 페이로드 없는 연결은 조용히, 첫 바이트가 오면 경보 + PG로(진짜 출발지)
- 한계: 클라이언트가 먼저 말하는 프로토콜(PG·HTTP·Redis)에만 됨(SSH는 서버가 먼저 말함)
- **두 기술의 분리**(11/23): report-sync 하나가 미끼 계정(Illusive T5)과 연결(Attivo)을 같이 실어 스위치가 엉킴 → 4가지 조합으로 분리, 디코이 이름 풀이는 두 기술이 공유

## 12. 투영(Acalvio — 센서 + 중앙 팜 + 터널)
- **L2 / L3**
  - 고민: 벤더 원본처럼 L2 브리지 / L3
  - 선택: **L3**(11/22~23) — VPC엔 L2 브로드캐스트 도메인이 없음(ARP는 하이퍼바이저, 패킷은 그 IP를 가진 ENI로만). DHCP·NetBIOS 같은 브로드캐스트 발견은 VPC가 원래 전달하지 않아 단서가 아님(실측)
  - 원본이 L2인 이유: 온프레미스 VLAN을 팜까지 브리지하면 디코이가 그 구간의 진짜 L2 이웃이 됨(학습 로그)
- **센서**: 투영 주소를 **센서 자신의 주소로 두지 않음**(fail-safe — local 규칙을 옮길 필요 없음), WireGuard로 출발지 그대로 팜에. **디코이 하나 = NIC(ENI) 하나** — 여러 디코이가 같은 MAC으로 ARP 캐시에 묶이면 단서(11/23 실측), 디코이 NIC MAC = 투영 NIC MAC
- **터널이 남기는 흔적**(11/23 공격자 시점 실측): TTL 62, SYN-ACK MSS 1340, DF 1472 ping 소실, traceroute 무응답 → **TTL 홉 보정 + 터널 MTU = 구간 MTU(바깥은 IP 단편화) + MSS 조정 제거**. 장애를 고치려고 넣은 MSS 조정 자체가 단서였다
- **응답 경로**: 터널 수명 주기에 묶음(wg-quick PostUp) — 시작 스크립트에 두면 터널보다 먼저 돌아 경로표가 비고 응답이 LAN으로 새서 SSH 키 교환이 멈췄다(11/23). 터널이 없으면 응답을 버림(fail-closed, `unreachable` 예비 경로)
- **게이트웨이 .1**: 팜 자신의 주소로 두지 않음 — 두면 LAN에서 진짜 라우터의 ARP를 가로챔(11/23 구간 분리 때 발견) → 링크 로컬 + proxy ARP, `arp_ignore=1`
- **탐지 위치**(11/23 특허 원문 US9756075·US9836512): 디코이 망은 "격리되고 면밀히 감시", "디코이에 대한 모든 접근은 자동으로 의심" — **탐지는 디코이 밖(팜)**. 구현은 11/25

## 13. 팜 디코이의 형태
- 고민: A 컨테이너(systemd-nspawn) 유지 / B 팜 안 KVM VM(벤더 방식) / C 디코이마다 EC2
- 선택: **B — KVM VM**(11/23 사용자) — 컨테이너는 `systemd-detect-virt` = systemd-nspawn, auditd 불가. C는 VPC에서 투영 주소를 디코이 OS에 따로 얹어야 해 새 단서

- **트랩은 아직 컨테이너**(결정 B를 트랩까지 넓히는 일은 남음)

## 15. 디코이를 만드는 공정
- **원칙**(11/23): 만드는 과정이 디코이에 흔적으로 남으면 안 됨 — 벤더가 "골든 이미지에서 찍어낸다"고 하는 이유
- 1단계: **공식 클라우드 이미지 + cloud-init 첫 부팅**(EC2 user-data 세팅과 같은 모양, 로그인 세션 아님 → 감사·sudo 기록 없음). 빌드 재료는 `/var/tmp`(`/run`은 noexec), 공통 베이스는 진짜 서버처럼 `/tmp/tmp.XXXX`에서
- 2단계: **VM을 끈 디스크에 비부팅 nspawn**으로 역할 서사(파일 시각·DB 복원) — 게스트 커널이 안 돌아 게스트 로그에 안 남음
- 3단계: **봉인** — user-data를 기본형으로, cloud-init 캐시 삭제(instance-id는 유지 → 호스트 키 재생성 없음)
- seed는 ISO 대신 디스크 안(`/var/lib/cloud/seed/nocloud`) — ISO면 CD-ROM 2개·cidata 흔적
- 디코이 안 **moa-notify**: 회사 표준 구성 그대로(같은 구간 진짜 서버 설정 모양, 트랩 중계 끔). 탐지 판단은 팜이 함

## 16. 경보(moa-notify — 자체 제작, 항상 켬)
- 파이썬 표준 라이브러리만, **세 서버 + 모든 디코이 공통**(디코이에만 있으면 단서). 로그를 따라 읽다가 웹훅으로(Discord/Slack/json), 1분 한도
- 감시: PostgreSQL 접속(T1·T5), 트랩 중계(ports), 페이로드 관문(gate)
- **실패해도 감시는 멈추지 않음**(11/23): 웹훅 주소가 채워지지 않은 템플릿 값이라 경보 순간 데몬이 죽던 결함 수정
- 한계: 공격자가 root를 얻으면 에이전트를 끌 수 있음 → 그 전에 경보가 나가는지가 검증 포인트. 투영 디코이는 팜에서 탐지(디코이 밖)
- **목적지 탐지**(11/23 밤): 디코이 SSH 감시(접속 하나 = 경보 하나, 시도한 키 지문 포함 — 지문 → 미끼 대응은 서버 밖 `whois`, 서버엔 미끼 목록을 두지 않음), 실패한 키도 남기려고 공통 `LogLevel VERBOSE`
- **투영 디코이의 탐지 위치**
  - 고민: 디코이 안 moa-notify / 팜(디코이 밖)
  - 선택: **팜** — relay에서 디코이로 가는 새 연결을 nft로 기록 → 팜 경보 데몬. 디코이 안 데몬은 회사 표준 구성으로만(바깥 길이 없어 경보를 못 보냄 — 바깥 길을 열면 공격자도 씀)
  - 근거: Acalvio 특허(디코이 망은 "면밀히 감시", "모든 접근은 의심"), 공격자가 디코이를 장악해도 끌 수 없음
- **경보 수신**: 세 서버 웹훅을 환경 프로필 값 하나로 통일, 로컬은 호스트 수신기. 탐지 검사(`detect.py`)가 경로 5개를 실제로 건드려 도착 시간을 잼 — 모두 1.4초 이내(기준 60초)
- 관리 접속 소음(로컬 랩의 검사 도구 로그인)은 지금은 울리게 두고 11/30 오탐 단계에서(사용자)

- **감사(audit, 11/23)**: auditd 기록에서 `secret-files`·`persistence` 키 사건을 알림(프로세스·부모·auid·명령줄 포함 — 11/27 상관분석 재료). 거르는 것: 규칙 적재, 디렉터리 열기, sshd의 사전 인증 authorized_keys 읽기, 같은 프로세스·같은 파일 30초 안 반복. 모든 서버·디코이 켬(자체 설계)
