# 직전 프로젝트(Cowrie)에 대해 받은 피드백 — 원문 정리

이 프로젝트(Deceptive-2)는 아래 피드백에 대한 답이다. 방향이 흔들리면 여기로 돌아온다.

## 핵심 요약
- 허니팟(SSH 중심) 분석 프로젝트에 대해 결과 나열보다 시도 과정과 학습 내용을 중심으로 보고서를 구성해야 한다는 지적
- 프로젝트 기간과 마감 설정이 부족했고, 현업 기준의 평가 목표와 기준을 먼저 세울 필요가 있음
- 디셉션 기능을 직접 구현하고 공격 시나리오까지 검증하는 방향이 실무 어필에 더 적합

## 프로젝트 결과보고서 구성 방향
- 결과 수치보다 시도 과정과 배운 점이 중요함 [00:10]
- 공격 기법 개수나 업로드 파일 수 같은 숫자만으로는 역량이 드러나지 않음 [00:10, 02:40]
- SSH 하나에 4일을 쓴 것은 진행 속도가 느린 것으로 평가됨 [00:44, 00:54]
- 데이터 수집 목적과 활용 방향을 본인 관점에서 명확히 설명해야 함 [04:24]

## 프로젝트 진행 방식 문제
- 마감 없이 목표가 수정되고 진행이 늘어져 프로젝트가 중단된 경우가 많음 [01:56, 02:12]
- 기간과 세부 목표를 정해 두고 진행해야 함 [02:28, 02:40]
- 프로젝트 성공 판정 기준과 커버리지 범위를 미리 정해야 함 [07:08, 07:19]
- 채용 공고를 기준으로 필요한 보고서 수준을 확인하는 방식이 필요함 [07:23]

## 디셉션 프로젝트 방향
- 성능 비교보다 시중 디셉션 솔루션의 기능을 직접 구현해 보는 것이 중요함 [13:51, 14:03]
- 구현 후 실제 공격자가 반응하는지까지 검증해야 함 [14:05]
- 클라우드 환경에 직접 구축해 기능을 검증하는 방식이 제안됨 [13:24]
- 공격 데이터 규모는 의미가 제한적이므로 기능 구현과 활용 가능성을 강조해야 함 [21:08, 22:08]
- 기능별 체크리스트와 WBS를 작성해 단계적으로 진행하는 방식이 권장됨 [14:38, 19:21]

## 신입 채용 관점
- 주니어 채용은 직무 고정보다 잠재력과 회사 기여 가능성을 보고 뽑는 경우가 많음 [16:23]
- 포트폴리오에는 자신이 어떤 사람인지 분명하게 드러나야 함 [17:00]
- 현업에서 필요한 요소를 기준으로 평가받는 자세가 필요함 [08:19, 08:53]

## 할 일 (→ 이 프로젝트에서의 대응)
1. 시중 디셉션 솔루션 목록과 기능 매뉴얼 조사 → 기능 체크리스트 — `01-vendor-feature-map.md` (완료)
2. 선택한 디셉션 기능을 클라우드에 구현하고 실제 공격 시도로 동작 검증 — 기능 1~4 + 시나리오 1~3, 공격자 반응은 공개 노출 실험(`plan-wbs.md` 5절)
3. 프로젝트 기간, 성공 판정 기준, 커버리지 범위 정의 + WBS — `plan-wbs.md` (완료, 동결)
4. 목표 채용 공고 기준으로 보고서 수준과 방향 정리 — `03-job-mapping.md` (완료)
