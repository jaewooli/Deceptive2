## 계획 단계에서 나온 것 (11/19)

### 감시 장치가 디코이를 들키게 만든다 (기능 1 · 3)
- 질문: 실제 OS 디코이도 무엇 때문에 들키는가?
- 해본 것: 디코이에 auditd 감시 규칙과 Python 더미 DB 리스너를 올리는 설계
- 막힌 지점: `auditctl -l`로 감시 규칙이 그대로 보이고, 5432 포트를 PostgreSQL이 아닌 Python이 연다 → 감시 장치 자체가 구별 단서(T1518.001)
- 벤더 조사로 확인한 것: 이 문제에 대한 벤더의 답은 두 갈래
  1. **감시를 공격자가 닿는 곳에 두지 않는다** — Illusive는 엔드포인트에 에이전트 없이 미끼만 심고, 탐지는 미끼가 가리키는 트랩 서버·AD 로그인 실패에서. Acalvio는 디셉션을 중앙 팜에 두고 네트워크 존재만 투영
  2. **안에 두되 철저히 숨긴다** — Illusive의 고상호작용 디코이는 감시를 난독화된 루트킷으로 숨김
- 구현으로 확인할 것: 내 auditd·에이전트 노출 단서를 어디까지 줄일 수 있는가, 줄이지 못한 단서는 목적지 쪽 탐지로 대체 가능한가

### "디코이 투영"은 내가 생각한 것과 원리가 달랐다 (기능 1)
- 질문: 디코이 엔진 하나로 여러 디코이를 표현할 때 어디서 막히는가?
- 해본 것: 실제 OS 한 대에 보조 IP 여러 개를 붙이고 IP별로 다른 호스트명·페르소나를 주는 설계
- 막힌 지점: 로그인 후 호스트명·파일시스템을 IP별로 다르게 보이려면 컨테이너·네임스페이스가 필요 → 실제 OS 디코이 원칙과 충돌
- 벤더 조사로 확인한 것: Acalvio 특허의 "투영"은 **서로 다른 디셉션(별도 OS·에뮬레이션)을 중앙 팜에 여러 개 두고**, 각 VLAN의 경량 센서와 터널로 연결해 그 VLAN의 주소를 할당하는 방식. 즉 "OS 하나에 IP 여러 개"가 아니라 "디셉션 여러 개의 네트워크 존재를 옮겨 놓는 것". Attivo도 실제 OS 디코이를 "투영"한다고 설명
- 정리: 내 구현은 "투영"이 아니라 **단일 호스트 다중 주소(포트·배너 분리)**라고 정확히 부른다. 막힌 지점이 곧 벤더가 중앙 팜 구조를 택한 이유

### 미끼는 "열람"이 아니라 "사용"을 잡아야 한다 (기능 2)
- 질문: 미끼 열람과 사용 중 무엇을 잡아야 하는가?
- 해본 것: 프로세스 환경변수에 미끼 DB 비밀번호를 두고 `/proc` 열람을 감시하는 설계
- 막힌 지점: `ps`·`/proc` 열람은 정상 관리 작업과 구별되지 않아 오탐이 폭주
- 벤더 조사로 확인한 것: Illusive가 정확히 이 원칙. 미끼가 있는 엔드포인트가 아니라 미끼가 가리키는 목적지(트랩 서버, AD 로그인 실패)에서 탐지. SentinelOne도 미끼의 목적지는 블랙홀이어도 되지만 디코이가 있으면 현실감이 올라간다고 설명
- 구현으로 확인할 것: 같은 미끼를 호스트 쪽(auditd 열람)과 목적지 쪽(더미 DB 리스너·디코이 로그인) 두 방식으로 잡아 오탐·지연·노출을 비교

### 허니토큰에는 존재할 이유가 필요하다 (기능 2 AWS 키)
- 질문: 미끼가 존재할 이유는 어떻게 만드는가?
- 해본 것: OCI 서버에 AWS 키를 미끼로 두는 설계
- 막힌 지점: OCI 서버에 AWS 키만 있으면 공격자가 의도를 간파 → AWS 단일 환경 + "역할 전환 후 남은 장기 키" 서사
- 벤더 조사로 확인한 것: Illusive는 엔드포인트의 맥락(로그인 사용자, 실행 프로세스)을 보고 그 기계에 맞는 미끼를 고른다(특허). Acalvio는 주변 호스트명·사용자명·서비스를 분석해 속성을 생성. 미끼의 진정성은 미끼 하나가 아니라 주변 맥락과의 일관성에서 나온다
- 덧붙여: Canarytokens 공개 토큰은 TruffleHog가 계정 ID만으로 판별(호출 없이) → 출처 흔적도 맥락의 일부

### 클라우드 감사 로그 기반 허니토큰은 구조적으로 늦다 (기능 2 AWS 키)
- 질문: 클라우드 감사 로그 기반 허니토큰의 한계는 무엇인가?
- 해본 것: CloudTrail → EventBridge 경로 설계, 목표 5분
- 막힌 지점: CloudTrail 전달 지연 → 1-10-60의 1분 기준을 못 맞춤
- 벤더 조사로 확인한 것: Thinkst 공식 문서가 AWS 키 토큰 경보에 **2~30분 지연**을 명시(자기 AWS 계정의 CloudTrail 경유). 선두 제품도 이 지연을 감수 → 내 5분 목표는 오히려 빠듯한 편이고, 호스트 1차 탐지를 앞에 두는 2단계 구조가 의미 있음. 또 EventBridge는 읽기 전용 호출을 기본으로 전달하지 않는다는 지적 → 11/27 확인 항목이 실제로 중요

### 탐지와 대응: 관찰할 것인가, 바로 끊을 것인가 (기능 4 · 5)
- 질문: 디셉션 경보가 울리면 무엇을 해야 하는가?
- 벤더 조사로 확인한 것: 선택지가 셋으로 갈림. Canary는 경보만, Illusive는 트랩 응답을 늦춰(tar-pit) 시간을 벌고 출발지 엔드포인트에 포렌식 도구를 즉석 투입, Zscaler는 확정 위협으로 보고 즉시 격리
- 구현으로 확인할 것: 탐지 모드에서 세션 명령을 얼마나 얻는지, (여유 시) 더미 DB 리스너에 응답 지연을 넣으면 정보가 늘어나는지

## 구현 기록 (11/20~)

### 11/20 · 디코이 5432를 진짜 PostgreSQL로 정했더니, 사용자명을 잃는 경우가 생겼다 (기능 1 · 2)
- **한 줄**: 5432는 진짜 PostgreSQL 16 + `log_connections`로 정했다. 더미 리스너는 "흉내 낸 프로토콜의 응답 차이"(Bitter Harvest)와 "5432를 연 Python 프로세스"를 디코이에만 남기는데, 진짜 PG는 둘 다 지운다. 대가로 탐지가 프로토콜이 아니라 서비스 로그에 묶인다
- 질문: 실제 서비스로 바꿔도 미끼 계정 사용을 같은 품질로 잡을 수 있는가?
- 해본 것: 로컬 VM(Ubuntu 24.04.5, PG 16.15)에서 접속 5종 → `moa-notify`가 PG 로그를 읽어 알림
- 막힌 지점: 비밀번호 없이 접속해 인증 요청에서 끊으면(`psql -w`) PG 로그에 `connection received` 한 줄만 남고 **사용자명이 없다**. 더미 리스너는 인증 전에 오는 StartupMessage를 직접 읽으니 이 경우에도 사용자명을 안다. 비밀번호를 같이 보내면(T1 `.env` URL처럼) `password authentication failed for user "report_ro"`로 남는다. 또 libpq 기본(`sslmode=prefer`)은 인증 실패 후 비SSL로 재시도해서 접속 1번이 2건으로 잡힌다
- 벤더 설계에 대해 알게 된 것: "진짜처럼 보이는 것"과 "많이 보이는 것"이 부딪힌다. 에뮬레이션 디코이는 프로토콜을 직접 쥐고 있어 관측이 풍부하지만 구현 차이로 들키고, 실제 OS 디코이는 들키지 않지만 그 서비스가 로그에 남기는 만큼만 본다. 벤더가 넓이(에뮬레이션)와 깊이(실제 OS)를 나눠 파는 이유가 관측 쪽에도 있다

### 11/20 · 배포판 STIG 예제 규칙이 그 배포판 서버에서 중간에 멈췄다 (기능 1 · 3)
- 질문: 공통 auditd 규칙을 "보안 가이드를 따라 켜 둔 회사"처럼 만들 수 있는가?
- 해본 것: Ubuntu auditd 3.1.2 예제(10-base-config + 30-stig + 43-module-load)를 로컬 VM에 그대로 로드
- 막힌 지점: ① 30-stig의 `/etc/NetworkManager/` 감시가 Ubuntu 서버(디렉터리 없음)에서 오류 → **그 뒤 규칙 전부 미로드**(41줄 중 16줄). 같은 예제의 `12-ignore-error`로 해결 ② 30-stig는 전부 `auid>=1000`인데 Ubuntu에는 시스템 계정 `backup`(uid 34)이 원래 있다 → 미끼 계정 `backup`의 행동은 STIG 규칙에 안 잡힘. 명령 기록은 하한 없는 `auid!=unset` 공통 규칙으로
- 알게 된 것: 감시 흔적을 운영 서버와 같게 하는 일(변경 A)은 "같은 파일을 깐다"로 끝나지 않는다. 규칙이 실제로 로드됐는지(`auditctl -l` 줄 수)를 서버마다 확인해야 하고, 계정 번호 같은 작은 사실이 감시 범위를 바꾼다

### 11/20 · `shell=True`만 켜서는 명령 주입이 되지 않았고, PDF 변환만 깨졌다 (web-01 의도적 취약점)
- 질문: 영수증 PDF 함수를 "셸을 거치는 코드"로 바꾸면 그대로 명령 주입 취약점이 되는가?
- 해본 것: 인자 목록 호출 `[weasyprint, "--quiet", html, pdf]`에 `shell=True`만 추가
- 막힌 지점: POSIX에서 `shell=True` + 리스트는 **첫 원소만** `sh -c`의 명령이 되고 나머지는 `$0`, `$1`로 빠진다 → weasyprint가 인자 없이 실행 → 확인서 다운로드가 항상 500. 주입도 안 된다(셸이 파싱하는 문자열에 외부 입력이 없음). 명령을 `shlex.join()` 문자열로 넘겨 정상화했지만, 이것도 인자마다 따옴표를 씌워 주입은 막힌다. 게다가 파일명에 들어가는 `reservation.code`는 서버가 만드는 값이라 공격자가 정할 수 없다. 배포 쪽: Ubuntu 24.04 클라우드 이미지에는 `python3-venv`가 없어 `python3 -m venv`부터 실패(로컬 VM 확인) → `deploy/install.sh`에 포함
- 알게 된 것: 취약점은 "위험한 함수 호출"이 아니라 **공격자 입력이 셸 파싱에 닿는 경로**다. 그럴듯한 함정 서버를 만들려면 그 경로(어떤 입력이 어디로 흘러 명령 문자열에 붙는지)가 실제 운영 코드에서 생길 만한 모습이어야 한다

### 11/20 (이어서) · 서버 생성 code에 입력 경로를 달았더니 명령 주입이 실제로 터졌다 (web-01)
- 예약 변경 기능에서 `reservation.code`를 임의 문자열로 바꾸게 하니, `receipt.py`의 셸 문자열에 셸 메타문자가 닿아 명령 주입이 실행됨(PoC 확인). weasyprint가 실패해 500이 떠도 주입 명령은 그 전에 실행된다. 단 `code`가 `String(16)`이라 PostgreSQL에선 페이로드가 잘릴 수 있음(실 DB에서 확인 필요).

### 11/21 · 인프라를 Terraform 모듈로 코드화, NAT 없이 아웃바운드를 어떻게 주나 (인프라)
- 질문: NAT 게이트웨이 없이 internal 서버에 아웃바운드(패치·웹훅·SSM)를 어떻게 주고, 3대를 중복 없이 코드화하나?
- 해본 것: `host` 모듈 1개를 web/app/decoy 3번 호출(차이는 서브넷·타입·SG·보조 IP 파라미터). internal 서브넷도 `0.0.0.0/0 → IGW` + 공인 IP를 주고, 외부 유입 차단은 SG 인바운드로만. 디코이 보조 사설 IP 3개는 명시 ENI + EIP로.
- 막힌 지점: 명시 ENI를 붙이면 자동 공인 IP가 안 붙어 세 호스트를 EIP로 통일(보조 IP 때문에 어차피 ENI 명시 필요). terraform 미설치 + 계정 미확인이라 `validate`/`plan` 미검증 — EIP↔IGW 생성 순서, SSM AMI 파라미터 경로는 apply 때 확정해야 함.
- 알게 된 것: "internal"이 라우팅 격리가 아니라 **SG 격리**라는 게 no-NAT 설계의 핵심 트레이드오프(SG 한 줄 틀리면 바로 노출). 실무/벤더가 NAT를 쓰는 이유 = 이 "비용 대 안전" 트레이드오프를 비용을 주고 사는 것. detection-as-code처럼 인프라도 모듈+파라미터로 중복을 없애면 세 서버 동일성(변경 A)을 코드가 보장한다.

### 11/21 · 앱을 고치면 미끼 서버의 "과거 git 이력"도 고쳐야 한다 (web-01 진정성)
- 질문: `servers/webapp`에 예약 변경 기능을 넣었는데, `/srv/app` 서사용 커밋 이력(`build_history.py`)은 어떻게 맞추나?
- 해본 것: 도구를 돌리니 "새 파일(reservation_edit.html)이 어느 단계에도 없음"으로 실패. 예약 변경을 **2025-10-21 새 커밋(stage 14)**으로 추가하고, 그 전 단계에선 `updated_at`·`can_modify`·edit 라우트·예약 변경 링크를 벗겨내는 변환을 넣음. dep 커밋은 15·16으로 밀어 날짜 순서 유지.
- 막힌 지점: 새 기능을 아무 날짜에나 붙이면 DAG 순서(커밋 부모-자식)와 작성자 날짜가 어긋나 `git log --graph`에서 들통난다. 그래서 **커밋을 시간표의 올바른 자리(S3 전환 2025-09 다음)에 끼워야** 했다.
- 알게 된 것: 운영 서버와 구별되지 않으려면 코드뿐 아니라 **이력의 진정성**도 유지해야 하고, 그건 앱을 바꿀 때마다 드는 지속 비용이다. 벤더가 "골든 이미지·자동 블렌딩"으로 이 수작업을 없앤 이유가 여기서 보인다(기능 1 깊이 분석과 연결).

### 11/21 (11/22분) · 백신 검사 한 번이 1GiB 서버를 죽였다 — 디코이 비용은 디코이가 아니라 "운영 서버와 같아야 하는 것"이 정한다 (인프라 · 기능 1 · 기준선)
- 질문: 공통 에이전트 세트 + 역할 서비스 + 기준선 정상 작업을 동시에 돌려도 설계한 인스턴스 크기(디코이 t3.small, web·app t3.micro)에서 버티는가?
- 해본 것: 로컬 QEMU VM(2GiB / 1GiB, 스왑 없음 = EC2 Ubuntu AMI 기본)에 공통 베이스 + SSM·CloudWatch 에이전트 + 역할(디코이: PG + moa-notify + sshd 4개, app: PG + `pg_dumpall`, web: nginx → gunicorn)을 올리고, 5분 동안 로그인 실패 폭주 + execve 반복 + `clamscan -r /`(`infra/loadtest/`)
- 막힌 지점: 디코이(2GiB)는 최저 491MiB가 남아 통과. 1GiB에서는 app·web 모두 **clamscan이 OOM으로 죽음**. 부하를 다 빼고 clamscan 혼자 `/etc`만 검사해도 죽었다. 시그니처 DB를 올리는 데 약 1GB가 필요한데(2GiB에서 RSS 984~1117MiB), 공통 에이전트가 뜬 1GiB 서버의 여유는 약 560MiB. 가장 큰 상주 프로세스는 CloudWatch 에이전트(약 140MiB). 스왑 1GiB를 붙이면 OOM은 사라졌지만 쓰래싱으로 600초 안에 검사가 끝나지 않았다. 측정 쪽에서도 하나: OOM 수를 `journalctl -k`로 셌더니 메모리 압박 중에 journald가 늦게 기록해서 **0으로 나왔다** → `dmesg`로 셈
- 결정: 세 서버에 **ClamAV 매일 전체 검사 cron**을 두고 web-01·app-01을 t3.small로(약 +$8.7, 비용은 후순위). 중간에 "clamscan은 시험용일 뿐"이라며 micro로 되돌렸는데, 따져 보니 거꾸로였다 — 백신을 깔아 두고 한 번도 검사하지 않는 서버가 오히려 진짜 서버답지 않다. 진짜 서버라면 정기 검사가 돌고, 그 검사가 매일 미끼 파일을 연다
- 덧붙여 배운 것: 오탐 시험에 쓰는 "정상 작업"은 내가 따로 흉내 내는 것이 아니라 **서버에 실제로 걸려 있는 작업**이어야 한다. 그래야 "열람 감시는 정상 운영에서 매일 오탐을 낸다"가 시험이 아니라 사실이 된다
- 알게 된 것: 실제 OS 디코이를 "운영 서버와 구별되지 않게"(변경 A) 만들면, 디코이와 그 주변 서버의 크기를 정하는 것은 디코이 서비스(PG)가 아니라 **운영 서버라면 당연히 돌릴 가장 무거운 정상 작업**(백신 전체 검사)이다. 진정성의 비용이 메모리로 청구된다. 에뮬레이션 디코이나 중앙 팜 + 투영이 대량 배치에서 싼 이유가 여기 있다

### 11/21 (11/22분) · 시간대를 바꿨더니 auth.log에 UTC와 KST가 섞였다 (기능 1 진정성)

### 11/22 · 디코이에만 감시 장치가 생긴 건 디코이를 손대서가 아니라 app-01을 안 손대서였다 (기능 1 진정성)
- 질문: 공통 베이스 한 벌(변경 A)로 만든 디코이와 app-01은 감시 흔적이 정말 같은가?
- 해본 것: 진정성 검증 세트(`validation/collect.sh`·`probe.sh`·`compare.py`)를 만들어 로컬 VM 두 대에 첫 실행. 39개 항목 중 디코이 전용 단서 17개, 공통 단서 12개
- 막힌 지점: SSH·PG 바깥 응답과 패키지·audit 규칙은 같았는데, **감시 흔적 5개가 디코이에만** 있었다. 디코이 쪽 실수가 아니었다. 공통으로 정한 moa-notify를 app VM에 안 깔았고, 어제 공통 베이스에 ClamAV cron을 더한 뒤 app VM에는 base를 다시 안 돌렸다. "같은 파일 한 벌"을 저장소에 두는 것만으로는 서버가 같아지지 않는다 — **고친 뒤 모든 서버에 다시 배포해야** 같아진다. 측정 도구도 두 번 속았다: 이미지에 원래 있는 빈 `/var/log/dist-upgrade` 디렉터리를 "업그레이드 기록 있음"으로 읽었고, `vm.sh`가 켤 때마다 instance-id를 새로 만들어 SSH 호스트 키를 다시 만든 것(구축 흔적 오염)을 처음엔 서버 문제로 볼 뻔했다
- 알게 된 것: 디코이를 운영 서버와 구별 안 되게 유지하는 일은 디코이 관리가 아니라 **환경 전체의 설정 어긋남(드리프트) 관리**다. 벤더가 디코이·미끼를 중앙 콘솔에서 배포·갱신하는 이유이고, 이 프로젝트가 미끼를 손 대신 SSM/Ansible로 배포하기로 한 변경 C의 근거가 측정으로 확인됐다. 그리고 단서를 세는 도구는 단서보다 먼저 검증해야 한다 — 측정이 틀리면 "보완 전후 단서 수"가 의미를 잃는다

### 11/22 (이어서) · 디코이를 재는 도구가 디코이에 "honeypot"을 써 넣고 있었다 (기능 1 진정성)
- 질문: 서버 안에 프로젝트 용어가 남아 있지 않은가(F4)?
- 해본 것: 영어 용어(decoy·bait·honeypot…)로 grep → 0건. 한국어 용어를 더하니 디코이에 남은 저장소 `~/servers`(README에 "디코이"·"미끼")가 나옴 — 로컬 VM에 파일을 올리는 `vm.sh push`가 남긴 것
- 막힌 지점: 지우고 다시 재는데 auth.log·audit.log에서 용어가 계속 나왔다. **측정 명령 자체가 원인**이었다. `sudo grep "디코이|미끼"`는 sudo가 명령줄 전체를 auth.log에 남기고, 수집 스크립트의 grep 인자는 세 서버 공통 auditd 규칙(로그인 세션 execve)이 audit.log에 남긴다. 측정을 돌릴 때마다 "honeypot|decoy|bait"가 서버 로그에 쌓이고 있었다. 용어 목록을 셸 내장 `printf`로 만들어 `/dev/fd`로 넘기니 인자에 남지 않았다(측정 전후 증가 0)
- 알게 된 것: 디코이 운영의 적은 디코이 자체보다 **디코이를 다루는 사람과 도구가 남기는 흔적**이다. 관리 접속, 점검 스크립트, 배포 파일이 모두 서버 기록에 남고, 감시를 잘 걸어 둘수록(execve 기록) 그 흔적도 더 잘 남는다. 벤더가 디코이를 고객이 직접 만지지 않게 하고 중앙 콘솔·에이전트 채널로만 관리하는 이유를 몸으로 겪었다. 이 프로젝트에서는 SSM/Ansible 배포(변경 C) 뒤 배포 파일을 지우는 것, 점검 명령에 용어를 넣지 않는 것을 규칙으로 둔다

### 11/22 (이어서) · 오래된 정상 서버는 만들 수 없었다 — 그래서 서사를 서버에 맞췄다 (기능 1 진정성 · 한계)
- 질문: 세 서버 모두 "지난달에 만든 서버"로 보이는 공통 단서 13개를 어떻게 없애나?
- 해본 것: 옛 AMI + 로그 위조(wtmp·회전 로그·apt 이력·시계를 돌려 ctime까지)를 항목별로 따져 봄. 대부분은 가능했다. 그러나 서버 안에서 권한 없이 보이는 **IMDS 인스턴스 시작 시각(`pendingTime`)** 은 AWS가 주는 값이라 바꿀 수 없고, 클라우드 공격자는 들어오자마자 IMDS를 조회한다(T1552.005). 로그를 정교하게 꾸밀수록 이 한 줄과의 모순이 커진다
- 막힌 지점: "오래 운영된 정상 서버"는 시간을 들여야만 만들어진다. 프로젝트 기간 안에는 불가능
- 결정: 서사에 **2026-11 서버 일괄 재구축**(데이터·홈·호스트 키는 rsync -a로 이전, 옛 백업 서버도 확인 없이 같이 옮김)을 넣고, 한계로 기록. 가짜 데이터는 옮겨 온 것에만 만들었다. 그 덤프를 만들면서 또 배웠다: 지금 `pg_dump`로 만들면 2024년 덤프 머리말에 2026년 PG 버전과 2025-08에 생긴 `\restrict` 줄이 찍힌다. 과거의 데이터를 만들려면 **그때의 도구**를 흉내 내야 한다(Launchpad 배포 이력으로 날짜별 버전)
- 알게 된 것: 시간은 위조하기 가장 어려운 재료이고, 클라우드는 그 시간을 공급자가 증명해 준다. 그래서 디코이의 진정성은 "오래돼 보이게"가 아니라 **"이야기가 인프라와 맞게"** 만들어야 한다. 벤더가 고객의 실제 운영 환경·골든 이미지 안에서 디코이를 만드는 것은 이 시간 문제를 고객 환경에 떠넘기는 방법이기도 하다. 그리고 숫자를 셀 때 주의할 점: 이번에 줄어든 단서 23개 중 11개는 서버가 아니라 서사를 바꿔서 없어졌다 — 보고서에서는 둘을 나눠서 쓴다

### 11/22 (이어서) · IP 4개는 스캔에선 4대, 로그인 한 번에 1대 — 벤더가 중앙 팜을 택한 이유 (기능 1 넓이)
- 질문: OS 하나에 사설 IP 4개(t3.small ENI 한도)를 붙이면 어느 단계까지 여러 서버처럼 보이고, 어디서 무너지는가?
- 해본 것: IP별 sshd(각자 호스트 키) + IP별 포트 조합(PG는 2개 주소에만 listen). 주 sshd는 Ubuntu 24.04 `ssh.socket`만 주 IP로 좁혀 `sshd_config`는 app-01과 같게 둠. 스캐너처럼 주소마다 배너·KEX·호스트 키·포트를 잼
- 막힌 지점: 처음 고민은 "sshd 하나 + iptables(로그인 뒤 흔적 없음)" vs "IP별 sshd(로그인 뒤 흔적 있음)"였다. 그런데 IP를 늘린 목적이 넓이(스캔에서 여러 대로 보여 디코이에 닿을 확률을 높임)라면 앞의 것은 처음부터 성립하지 않는다 — 같은 호스트 키 4개는 스캔 한 번에 1대로 묶인다. 그리고 로그인 뒤 무너지는 것은 숨길 문제가 아니라 재야 할 지점이었다. 실제로 로그인하자마자 주소 4개·리스너 6개·IP가 박힌 sshd 3개가 보였고, 내 검사 세트는 처음엔 그걸 못 봤다(프로세스 이름만 비교, 템플릿 유닛 누락)
- 알게 된 것: 넓이는 **로그인 전 단계**(스캔·배너·키)에서만 산다. 경보는 처음 닿을 때 울리니 탐지 목적엔 그걸로 충분하지만, 닿은 뒤 공격자를 붙잡아 두는 깊이는 OS를 공유하는 순간 사라진다. 그래서 벤더는 넓이와 깊이를 분리하고, Acalvio는 서로 다른 디셉션 여러 개를 중앙 팜에 두고 네트워크 존재만 각 구간에 옮긴다 — 로그인 뒤에도 서로 다른 기계여야 하기 때문이다. 내 방식은 비용 0으로 넓이를 얻는 대신 "로그인 = 정체 노출"을 받아들인 것

### 11/22 (이어서) · 진짜 투영을 만들었다 — 바깥에선 진짜, 안에선 "컨테이너" 한 줄 (기능 1 넓이 · 벤더 투영)
- 질문: 벤더 투영(센서 + 중앙 팜)을 AWS 구조 그대로 만들면 어디까지 진짜 서버처럼 보이는가? 단일 호스트 다중 주소와 무엇이 다른가?
- 해본 것: sensor(투영 주소만 차지, 서비스 없음) → WireGuard → farm(systemd-nspawn OS 컨테이너 `stg-01` 옛 스테이징: sshd·nginx→gunicorn·PostgreSQL, 2025-05-12 커밋, db-backup-01 덤프 복원, deploy 히스토리). 로컬 VM 3대(공격자·sensor·farm)
- 막힌 지점: ① VPC엔 L2가 없어 벤더의 L2 터널 대신 L3 정책 라우팅 — local 테이블보다 먼저 투영 주소를 가로채는 규칙이 커널 ARP 판단까지 가로채 ARP 응답이 사라짐 → proxy ARP(AWS는 하이퍼바이저가 ARP를 답해 무관) ② QEMU socket listen/connect 링크가 한 방향만 흐름 → UDP dgram ③ debootstrap은 출시판을 깔아 SSH 배너가 다른 서버(`13.20`)와 달랐고(`13`), sshd가 비밀번호 인증을 받음 ④ 컨테이너 DNS(팜의 127.0.0.53을 그대로 넘김)
- 결과: 바깥(스캔·배너·웹·PG·출발지 보존)은 진짜 서버와 같다 — 다중 주소와 달리 로그인 뒤에도 **다른 기계**다(hostname·데이터·프로세스가 db-backup-01과 다름). 그러나 로그인하면 `systemd-detect-virt` 한 줄이 "systemd-nspawn"을 말하고, audit 규칙이 0개다. 커널 audit은 컨테이너별로 나뉘지 않아 auditd를 돌릴 수 없다
- 알게 된 것: 투영의 진정성은 **팜이 디코이를 무엇으로 만드느냐**가 정한다. 컨테이너는 싸고 많이 만들 수 있지만 커널을 공유해서, 운영 서버와 같아야 하는 감시(auditd)와 가상화 정체가 무너진다. Attivo BOTsink가 팜 안에 VM(골든 이미지)을 두는 이유, Smokescreen이 대부분을 에뮬레이션으로 하고 깊이가 필요한 곳만 실제 OS로 하는 이유가 같은 축 위에 있다 — 넓이(개수)를 늘릴수록 디코이 하나의 깊이가 얕아진다. AWS t3는 중첩 가상화가 안 돼 팜 안 VM이라는 벤더 해법을 그대로 쓸 수 없다(한계)

### 11/22 (이어서) · 맥락 기반 미끼 배포는 "진짜로 쓰인 서버"에서만 성립한다 (기능 2 · Illusive 배포)
- 질문: Illusive처럼 기계마다 맥락을 읽어 미끼를 고르고 맞추는 배포를 Ansible로 만들면 무엇이 필요한가?
- 해본 것: 읽기 전용 맥락 수집(값은 안 읽고 이름·형식만) → 유형별 규칙 → 표시 없이 적용(시각 보존) → 레지스트리 → 드리프트(경보+복구)·교체(옛 ID retired)·회수. 공격자처럼 미끼를 따라가 디코이 로그인까지 확인
- 막힌 지점: ① 첫 실행에서 규칙이 **아무것도 두지 않았다** — 로컬 web-01 deploy엔 나가는 ssh 흔적이 없고 앱 DB가 SQLite. 정상 서버 사용 흔적(배포·DB 확인 히스토리, known_hosts, 실제 app-01 PG 연결)부터 만들어야 했다 ② 규칙 오판 셋: `~/.ssh`만 있으면 ssh를 쓴다고 봄(cloud-init `authorized_keys`뿐인 ubuntu), uid로 서비스 계정을 걸러 postgres를 못 봄, cron 줄에 `aws` 글자만 찾아 스크립트 속 aws를 못 봄 ③ 미끼를 따라가니 히스토리엔 `ssh db-backup-01`이 있는데 known_hosts엔 없어 "처음 보는 호스트" 질문이 떴다 ④ 히스토리 미끼를 줄 단위로 중복 제거하다가 **원래 히스토리의 exit 줄을 전부 지웠다** ⑤ 회수 뒤 미끼가 만든 빈 파일이 남음 ⑥ Ansible `blockinfile`은 관리 표시를 남겨 쓸 수 없었다
- 알게 된 것: 벤더의 맥락 기반 배포가 강한 이유는 규칙보다 **맥락이 진짜라는 것**이다 — 고객 단말은 실제로 쓰이니 미끼가 실제 사용 흔적 사이에 자연스럽게 섞인다. 랩에서는 그 맥락 자체를 만들어야 해서, 미끼보다 정상 서버 진정성이 먼저다. 또 미끼는 혼자 진짜일 수 없고 주변 흔적(known_hosts·세션 경계·파일 시각)과 맞물려야 한다 — 공격자는 미끼를 "따라가 보는" 순간 그 맞물림을 시험한다. 서사 결정(옛 키 삭제)이 규칙과 부딪히는 자리는 규칙을 고치지 않고 제약으로 막아 이유를 남겼다
