## 2. 프로젝트 정의
AWS에 가상 회사 인프라를 만들고, 상용 디셉션 제품의 핵심 기능을 직접 구현한 뒤, 내부 침투 공격 시나리오로 탐지가 되는지 검증한다.

### 직전 보고서에서 이어지는 설계 근거
- 에뮬레이터는 산술 확장 등 셸 동작 검사 하나로 판별됨, 검사 하나 실패 시 공격자가 업로드 중단 → 디코이는 실제 OS (실제 OS는 셸 동작 검사를 구조적으로 통과하므로, 다음 관문은 "사람이 쓰지 않는 서버 티"를 없애는 것)
- 실제 작업은 명령 로그 밖(ld.so.preload, cron.d, shadow, 셸 시작 파일, 숨김 바이너리) → 결과 기반 감시
- 봇은 30초 안팎에 반입·실행·삭제 → 이벤트 시점 증거 보존이 이상적(P1, 아래 참고)
- 인터넷 봇은 자격증명 미끼를 건드리지 않음 → 허니토큰은 사람·표적형 공격자 탐지용 (단, 관찰 대상은 SSH 자동화 봇뿐 — 웹 경로 공격자는 공개 노출 실험으로 확인)
- 반입은 기존 SSH 연결 위 SFTP → 외부 통신 차단만으로는 부족
- 한계: 인터넷 봇 데이터로는 내부 표적형 공격자를 말할 수 없음 → 직접 시나리오로 검증

### 벤더 교차 분석에서 나온 설계 원칙 (상세: `docs/01-vendor-feature-map.md` 2절)
1. **배포 채널**: 기업 디셉션의 진짜 비용은 미끼를 수천 대에 깔고 유지하는 경로. Zscaler·SentinelOne은 기존 ZTNA·EDR 에이전트에 얹고, Illusive는 에이전트 없이 원격 관리 접근으로 기계별 맞춤 미끼를 배포 → **미끼는 이미 쓰는 관리 채널(SSM/Ansible)로 배포** (변경 C)
2. **진정성 × 규모 × 비용**: 셋을 다 잡은 벤더는 없고, 모두 "넓이(디코이 개수)"와 "깊이(실제 OS)"를 분리 → **단일 호스트 다중 주소(넓이) / 실제 OS 디코이(깊이)로 역할 분리** (변경 B)
3. **감시 노출의 조건**: 감시 장치가 단서가 되는 것은 "있어서"가 아니라 "디코이에만 있어서". EDR·ZTNA 에이전트는 정상 단말에도 있으니 단서가 아님 → **디코이의 감시 흔적을 운영 서버와 동일하게** (변경 A)
4. **오탐률이 자동 대응 수준을 결정**: Zscaler의 "경보 = 확정 위협 → 자동 격리"는 오탐 0일 때만 성립 → **미끼 유형별로 자동 차단 가능 여부를 오탐 기준선으로 판정** (변경 D)
5. **탐지 후 가치는 출발지에**: Illusive는 포렌식을 디코이가 아닌 공격자 출발 엔드포인트에서 즉석 수행 → **경보 시 출발 인스턴스 포렌식 스냅샷** (변경 E)
6. **위생과 디셉션은 경쟁 관계**: 실제 남은 자격증명이 많을수록 미끼가 선택될 확률이 떨어짐 → **시나리오 전 실제 남은 자격증명 점검** (변경 F)
- 보조 근거: 벤더들은 디코이 판별 불가를 주장하지만 조사한 공개 자료에서 측정 방법을 찾지 못함 → 구별 단서를 직접 측정·공개. 공개 허니토큰 서비스는 계정 ID로 판별됨 → 내 AWS 계정 사용. 클라우드 감사 로그 기반 토큰은 선두 제품도 공식적으로 2~30분 지연 → 호스트 1차 + 클라우드 2차 2단계 탐지

## 3. 구현 기능 (상용 제품 메커니즘과 대응)
1. **실제 OS 디코이(깊이) + 단일 호스트 다중 주소(넓이) + 구별 가능성 측정(진정성 검증 세트)**
   - **깊이 — 실제 OS 디코이**: db-backup-01. 핵심은 실제 운영 서버와 구별되지 않는 것 ↔ Attivo BOTsink(실제 OS·골든 이미지), Illusive 고상호작용 VM, Zscaler RDP 디코이
   - **넓이 — 단일 호스트 다중 주소(변경 B)**: ENI 보조 사설 IP 2~3개(t3.small ENI당 IPv4 4개 확인, 11/19), IP별로 **포트·배너만 분리** — iptables + IP별 sshd 인스턴스(각자 sshd_config, `ListenAddress`, `VersionAddendum`, 로그인 Banner) 및 IP별 서비스 바인딩
     - Acalvio·Attivo의 "투영"과 원리가 다름을 명시: 벤더는 서로 다른 디셉션 여러 개를 중앙 팜에 두고 네트워크 존재만 각 구간에 옮김, 나는 OS 하나에 주소만 여러 개 → 로그인 후 `hostname`·`uname`·프로세스 목록이 같아지는 한계가 곧 벤더가 중앙 팜을 택한 이유(학습 로그 대상)
   - **진정성 검증 세트 = "디코이를 실제 서버와 구별할 수 있는가"를 재는 검사 묶음**
     - 셸 동작 검사(직전 보고서의 산술 확장, `$$`, `set --`, 함수 정의 등)는 에뮬레이터와 실제 셸을 가르는 검사라 실제 OS는 당연히 통과 → 출발점으로 한 줄만 기록, 측정 대상 아님
     - 측정 대상(실제 OS 디코이를 알아채는 단서):
       - 사용 흔적: uptime, `last`/`wtmp` 로그인 이력, bash_history 분량·자연스러움, 파일 생성 시각 분포(전부 같은 날인지), 로그 누적량, 패키지 설치 이력
       - 연결 흔적: `ss`·ARP 이웃·known_hosts에 실제 통신 상대가 있는지
       - **감시 흔적 차이(변경 A)**: 감시 장치가 "있는지"가 아니라 **운영 서버(app-01)와 다른지**를 측정. 설치 에이전트·서비스 목록, `auditctl -l` 규칙 목록, 감시 관련 프로세스·설정 파일을 app-01과 비교해 디코이에만 있는 항목을 센다(예: 미끼 계정 전용 auditd 규칙, 5432를 연 Python 프로세스)
       - 이야기 일관성: "S3 전환 후 정리되지 않은 옛 DB 백업 서버"라면 옛 덤프 파일·중단된 rsync 흔적·디스크 사용량이 맞는지, 인스턴스 메타데이터·IAM 역할·설치 패키지·자격증명 파일이 같은 이야기를 하는지 (회사 서사: `02-infra-design.md` 4절)
     - 근거: ATT&CK T1497.001(시스템 검사), **T1497.002(사용자 활동 기반 검사)**, **T1518.001(보안 소프트웨어 탐색)**. 항목마다 출처(ATT&CK / 공개 연구·도구) 표시
     - **측정 방법: 같은 검사를 디코이와 비교 기준 서버에 돌려 결과가 다른 항목(= 구별 단서)을 센다**
       - 비교 기준: 실제로 오래 운영된 서버(본인 개인 서버, 읽기 전용 검사만) + app-01(감시 흔적 비교의 기준)
       - 결과: "구별 단서 N개 → 보완 후 M개". 단서를 하나씩 없애는 과정이 기능 1의 작업
     - **감시 흔적 동일화 원칙(변경 A)**: web-01·app-01·디코이에 **같은 에이전트 세트(SSM 에이전트, CloudWatch 에이전트, auditd)와 같은 기본 auditd 규칙 세트**를 설치. 디코이 전용 규칙은 최소화하고, 피할 수 없는 디코이 전용 흔적(더미 DB 리스너)은 "목적지 탐지의 대가"로 명시 기록
2. **브레드크럼 · 허니토큰 · 자격증명 저장소 미끼** (함정 목록 T1~T6: `02-infra-design.md` 5절)
   - **배포 채널(변경 C)**: 모든 미끼는 손으로 심지 않고 **SSM(Run Command/State Manager) 또는 Ansible**로 배포·교체·회수. 미끼 정의(위치, 내용 템플릿, 고유 ID, 가리키는 목적지)는 Git의 코드로 관리 ↔ Illusive의 원격 맞춤 배포, Zscaler·S1의 기존 에이전트 재사용
   - 파일 미끼: `.env`, `~/.ssh/config`, `~/.bash_history` → db-backup-01
   - 자격증명 저장소·메모리 미끼 ↔ Illusive·ThreatStrike·S1 Identity의 자격증명 저장소 미끼를 Linux로: `ssh-agent`에 미끼 키, 실행 중 프로세스 환경변수·인자에 미끼 DB 접속 정보(`ps`로 보임). (`~/.git-credentials`는 11/19 제외 — git 서버가 없어 사용 시점 탐지 목적지 없음)
   - **메모리 미끼 탐지 방식(확정)**: `/proc` 열람이나 `ps` 실행은 감시하지 않음(정상 관리 작업에서 오탐 폭주). 대신 **미끼 DB 계정으로 접속을 시도하는 순간**을 잡는다(목적지 탐지, Illusive 트랩 서버와 같은 원칙) → db-backup-01에 경량 더미 DB 리스너(Python 소켓, PostgreSQL 5432). 접속 시작 메시지에서 사용자명을 읽어 미끼 계정이면 경보. 미끼 키도 같은 원칙(사용 시점 탐지) — (**11/20 결정: 진짜 PostgreSQL 16 + `log_connections`로 교체**, 리스너 대신 PG 서버 로그에서 사용자명을 읽음, `02-infra-design.md` 2절)
   - **AWS 키 서사(확정, AWS 단일 환경)**: app-01은 IAM 역할 `backup-writer`로 매일 S3 백업(실제 동작, IMDSv2 인증, 키 파일 없음)
     - 미끼 = 역할로 전환하기 전에 쓰던 **장기 액세스 키**가 `~/.aws/credentials`의 `[backup-legacy]` 프로필로 남아 있음(IAM 사용자 `backup-legacy`, 권한 없음). 공격자가 쓰면 AccessDenied
     - 흔적: 키 방식 이전 백업 스크립트(주석 처리), 전환 시점 히스토리·변경 메모 — 11/27 중 1시간 상한
     - 실제 침해 사고에서 흔한 "역할 전환 후 정리되지 않은 장기 키" 패턴 = 위생 실패 사례(변경 F와 연결)
   - AWS 키 2단계 탐지: 1차 호스트(파일 열람, 60초) / 2차 CloudTrail(단일 리전 추적) → EventBridge → Lambda → 웹훅(5분, CloudTrail 전달 지연이라는 구조적 한계). 읽기 전용 호출 전달 여부 먼저 검증, 안 되면 CloudTrail → CloudWatch Logs 지표 필터
   - 같은 미끼를 **호스트 쪽(auditd 열람)과 목적지 쪽(디코이 로그인·더미 DB 리스너·CloudTrail)** 두 방식으로 잡아 오탐·지연·노출을 비교 → 학습 로그 대상
3. **결과 기반 감시 (P0/P1 분리)**
   - **P0(필수)**: `authorized_keys`, `/etc/ld.so.preload`, `/etc/cron.d` auditd 감시
   - **P1(시간 남을 시)**: `/etc/shadow`, 셸 시작 파일, 숨김 실행 파일, **이벤트 시점 파일 사본 보존**(auditd는 변경 이벤트만 남기고 사본을 만들지 않음 → fanotify 또는 커스텀 데몬 필요)
   - 11/28 20:00까지 P0만 완료되면 P1은 버리고 보고서 "기술적 한계 및 향후 과제"에 기록
4. **경보, 침투 체인 상관분석, 출발지 포렌식**
   - HASSH 기반 행위자 묶기는 제외(실제 OS의 OpenSSH는 HASSH를 기록하지 않음, 패킷 분석기 별도 필요). 원청 관점에서 필요한 건 "어디가 털렸고 어디로 이동했나"
   - 상관분석: 미끼 고유 ID → 미끼가 있던 호스트 → 디코이 접속 출발 내부 IP → 사용 계정 → 이후 행동을 하나의 침투 체인 경보로 묶음
   - **디코이 세션 명령 기록**: 디코이는 정상 업무에서 아무도 로그인하지 않으므로 로그인 자체가 경보(P0). 로그인한 세션에서 실행된 명령(auditd execve, 미끼 계정 auid 기준)을 경보에 첨부하고, 그중 판별·정찰 명령(T1497 계열, T1518.001)은 경보 본문에 별도 표시. execve 규칙이 운영 서버에 없는 디코이 전용 흔적인지는 진정성 검증 세트에서 측정
   - **출발지 포렌식 스냅샷(변경 E)**: 경보가 나면 상관분석이 찾은 **출발 내부 IP의 인스턴스**에 SSM Run Command로 포렌식 스냅샷을 자동 수집해 경보에 첨부 — 프로세스 목록, 네트워크 연결, 최근 로그인, 최근 변경 파일, 셸 히스토리 ↔ Illusive의 "경보 순간 출발 엔드포인트에 포렌식 도구 투입". 수집 결과는 CloudWatch Logs/S3에 보관
5. **(여유 시) 대응 모드**
   - 탐지 모드(기본, 모든 시나리오 검증) / 차단 모드(출발 내부 IP를 보안 그룹·iptables로 격리, 별도 시나리오 4로만 검증), 설정 플래그로 전환, 경보에 모드 표시
   - **차단 모드 적용 조건(변경 D)**: 기준선에서 **오탐 0건이었던 미끼 유형에만** 자동 차단을 건다. 오탐이 1건이라도 있었던 유형은 억제 규칙 후에도 "경보만" ↔ Zscaler의 자동 격리가 성립하는 조건
   - 더미 DB 리스너 응답 지연(tar-pit)으로 포렌식 수집 시간 벌기(Illusive 트랩 서버 방식)

범위 제외: LLM 허니팟, Windows AD, 대규모 데이터 수집, AI 자동 배치, HASSH, `~/.git-credentials` 미끼, T-Pot 같은 외부 허니팟 플랫폼
여유 시: 대응 모드(차단, tar-pit), LLM 경보 요약(채용 공고 LLM 요구 대응), 결과 기반 감시 P1, **공개 노출 실험(5절, 12/2 저녁~12/4)**

## 5. 검증
- 시나리오(ATT&CK 기반, 커버리지 표는 `docs/01-vendor-feature-map.md` 6절 — **P0 표만 성공 기준 대상**), 모두 탐지 모드
  - **사전 점검(변경 F)**: 시나리오 실행 전 web-01·app-01에 미끼 외의 실제 자격증명(다른 AWS 프로필·키, 평문 비밀번호가 든 설정 파일, 불필요한 SSH 키)이 남아 있지 않은지 점검. 남아 있으면 제거 후 진행하고 보고서에 "원청이라면 실제 노출 제거가 먼저, 그 자리에 미끼"로 기록
  1. 웹 서버 침투 → 자격증명 탐색(파일·메모리 미끼) → 디코이로 횡적 이동(로그인 경보 + 세션 명령 첨부 + 출발지 포렌식), 미끼 DB 계정 접속 시도
  2. 남아 있던 장기 액세스 키(`backup-legacy`) 사용
  3. 관측된 봇 행동 안전 재현(SFTP 반입 → 실행 → ld.so.preload 등록 → 삭제)
  4. (여유 시) 차단 모드에서 시나리오 1 재실행 — 오탐 0 미끼 유형만 차단

- 룰·억제 규칙·미끼 정의·검증 세트는 Git으로 관리, 수정할 때마다 시나리오 재실행(회귀 테스트)

- **11/22 필수 확인**: 디코이에서 공통 에이전트 세트 + 웹훅 스크립트 + 디코이 DB(더미 리스너 또는 PostgreSQL) + IP별 sshd를 동시에 돌린 부하 테스트로 OOM 없이 안정적인지 확인. t3.micro 2대도 공통 에이전트 세트로 확인
- 진정성 비교 기준: 본인 개인 서버(OCI, 장기 운영) — 읽기 전용 검사만, VPC와 연결하지 않음
- 전환 사유: OCI 서버에 AWS 키만 있는 구성은 이야기 일관성이 깨짐, 채용 공고 3곳이 AWS 탐지 경험 요구, arm64·이중 클라우드 경보 경로 문제 해소. 대가는 ₩0 구성 포기
