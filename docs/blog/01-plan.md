# [초안] 허니팟을 보던 사람이 디셉션을 직접 만들기로 했다 — Deceptive-2 계획

> 한 줄: 직전 프로젝트(Cowrie SSH 허니팟)에 받은 피드백에 답하려고, 시중 디셉션 제품의 핵심 기능을 직접 만들고 공격자 앞에서 먹히는지 검증한다. 마감 12/4.

## 1. 지난 프로젝트와 받은 피드백
- 직전 프로젝트: Cowrie SSH 허니팟을 인터넷에 열고 봇 공격을 모아 분석 → https://deceptive.ddyoru.cloud/analysis/
- 받은 피드백(요지, docs/feedback.md)
  - 공격 기법 개수·업로드 파일 수 같은 **숫자로는 역량이 안 보인다** → 시도 과정과 배운 점을
  - **마감 없이 목표가 바뀌며 늘어졌다**(SSH 하나에 4일) → 기간·세부 목표·성공 기준을 먼저
  - 성능 비교보다 **시중 디셉션 기능을 직접 구현**하고, **실제 공격자가 반응하는지** 검증하라
- [채울 것] 피드백을 듣고 든 생각 한두 문단(내 말로). 특히 "포트폴리오에 내가 어떤 사람인지 드러나야 한다"를 어떻게 받아들였는지

## 2. 이번엔 무엇을 하나
- 목표: **AWS에 가상 회사를 만들고, 상용 디셉션 제품의 핵심 기능을 직접 구현한 뒤, 내부 침투 시나리오로 탐지되는지 검증**
- 진짜로 얻고 싶은 것: 기능을 만들어 보며 **벤더가 왜 그렇게 설계했는지(또는 왜 동의 못 하는지)** 깨닫기
- 가상 회사 "모아예약": 소규모 매장 예약 SaaS. 백업을 옛 서버(rsync)에서 S3로 옮긴 뒤, 옛 서버와 옛 키를 정리하지 않았다 — 이 "정리 안 한 흔적"이 디코이·미끼의 이야기
  - [채울 것] 구성도 그림(web-01 / app-01 / db-backup-01 + 센서·팜)
- 직접 구현할 벤더 기술(특허·데이터시트를 원문으로 확인)
  | 벤더 | 기술 | 한 줄 |
  |---|---|---|
  | Illusive | 맥락 기반 미끼 배포 | 서버마다 실제 사용 흔적에 맞춰 가짜 자격증명을 심는다 |
  | Illusive | 트랩 서버 중계 | 운영 서버의 안 쓰는 포트를 디코이로 넘긴다 |
  | Illusive | 출발지 포렌식 + tar-pit | 경보가 오면 "어느 서버의 어느 프로세스"인지 잡는다 |
  | Attivo | 실제 OS 디코이, 연결 테이블 미끼, 행동 기록 | 진짜 OS로 만든 디코이, 공격자 netstat에 보이는 연결 |
  | Acalvio | 투영 | 디코이는 한 곳(팜)에 두고 네트워크 존재만 여러 구간에 |
- 이전 프로젝트와 다른 점: 인터넷 봇 데이터가 아니라 **내부 침투자**를 상정. 봇 데이터로는 내부 표적형 공격자를 말할 수 없어서

## 3. 성공 기준을 먼저 정했다
- ATT&CK 기준 시나리오 3개(웹 침투 → 횡적 이동 / 남은 장기 AWS 키 / 관측된 봇 행동 재현)의 탐지 단계 100% 경보
- 호스트 경보 60초, AWS 키 경보 5분 이내
- 정상 작업으로 오탐 기준선 → 원인 분석 → 억제 후 0건, 탐지율 유지
- 디코이와 운영 서버를 구별할 단서를 **측정**하고 보완 전후를 보고
- 시나리오 1의 경보가 **하나의 침투 체인**으로 묶일 것
- [채울 것] 왜 이 숫자인지(예: 60초 = 1-10-60 규칙)

## 4. 늘어지지 않게 하는 장치
- 마감 12/4, 날짜별 WBS, 기능마다 **시간 상한과 드롭 기준**(넘으면 기간을 늘리지 않고 범위를 줄인다)
- 계획은 동결 — 새 기능 추가 금지, 바꿀 수 있는 건 드롭 기준 적용과 진행 기록뿐
- 매일 학습 로그: **질문 → 해 본 것 → 막힌 지점 → 벤더 설계에 대해 알게 된 것**
- 그리고 이 블로그
- [채울 것] 일정표 이미지(plan-wbs 7절)
