# [초안] 디코이는 디코이를 다루는 손에서 들킨다 — 진행 1 (11/20~11/23)

> 한 줄: 실제 OS로 디코이를 만들고 "운영 서버와 구별되는가"를 재 봤더니, 디코이를 들키게 하는 건 디코이 자체보다 **디코이를 만들고 재는 과정**이었다.

## 1. 왜 실제 OS 디코이인가
- 직전 프로젝트의 Cowrie(에뮬레이터)는 산술 확장 하나로 판별됐다 → 이번 옛 백업 서버 디코이(db-backup-01)는 **진짜 Ubuntu + 진짜 PostgreSQL**
- 대가: 에뮬레이터는 프로토콜을 직접 쥐고 있어 다 보지만, 실제 OS는 그 서비스가 로그에 남기는 만큼만 본다(PG 접속 실패 땐 사용자명을 잃는 경우) → 벤더가 넓이(에뮬레이션)와 깊이(실제 OS)를 나눠 파는 이유가 관측 쪽에도 있었다

## 2. "구별되는가"를 측정했다
- 진정성 검증 세트: 같은 검사를 디코이와 운영 서버(app-01)에 돌려 어긋나는 항목 = 단서. 43개 항목을 **봇 층**(자동)과 **사람 층**(이야기)으로 나눔
- 첫 측정(11/22): **봇 층 단서 0개**. 셸 동작·오류 형식·하드웨어·SSH/PG 응답이 바이트 단위로 같았다 → 실제 OS를 고른 것만으로 자동 층은 끝
- 사람 층: 디코이 전용 단서 17개 + 환경 전체 단서 12개 → 보완 뒤 2개 + 2개
- [채울 것] 측정표 이미지(validation/README 11/22)

## 3. 막힌 점들 — 이 글의 본론
### 3-1. 재는 도구가 디코이에 "honeypot"을 써 넣고 있었다
- 서버에 프로젝트 용어가 남았나 찾는 명령의 **인자에 그 단어 목록**을 넘겼더니, sudo와 auditd가 그 명령줄을 로그에 기록 → 측정할 때마다 서버에 "honeypot|decoy"를 써 넣음
- 깨달음: 디코이의 적은 **디코이를 다루는 사람과 도구의 흔적**. 감시를 잘 걸수록 그 흔적도 잘 남는다. 벤더가 디코이를 고객이 직접 못 만지게 하고 중앙 채널로만 관리하는 이유

### 3-2. 디코이에만 감시 장치가 있었다 — 디코이를 손대서가 아니라 운영 서버를 안 손대서
- 경보 데몬·백신 검사 cron이 디코이에만 → 운영 서버에 안 깔아서 생긴 단서
- 깨달음: 디코이 관리 = **환경 전체의 드리프트 관리**. 그래서 미끼·설정을 손이 아니라 배포 채널로

### 3-3. 오래된 서버는 만들 수 없었다
- 서사는 "2024년부터 운영"인데 OS는 2026년 이미지, cloud-init·저널·machine-id가 전부 "최근 구축"을 말함. 클라우드는 시간을 공급자가 증명해 준다
- 선택: 서버를 늙게 꾸미지 않고 **서사를 서버에 맞춤** — "2026-11 서버 일괄 재구축, 데이터는 옮겨 옴"
- 주의: 이때 줄어든 단서 중 절반은 서버가 아니라 **서사를 바꿔서** 없어졌다 → 둘을 나눠서 셌다
- 깨달음: 벤더가 고객의 실제 골든 이미지로 디코이를 만드는 건 이 시간 문제를 고객 환경에 맡기는 방법

### 3-4. 백신 검사 한 번이 1GiB 서버를 죽였다
- 운영 서버라면 돌릴 ClamAV 전체 검사를 디코이에도 → OOM. 디코이 크기를 정하는 건 디코이 서비스가 아니라 **운영 서버와 같아야 하는 가장 무거운 정상 작업**

### 3-5. IP 4개 → "진짜 투영"(Acalvio)
- 한 서버에 IP 4개: 스캔에선 4대, **로그인 한 번에 1대**(hostname·ip addr·프로세스가 같음)
- 그래서 투영: 센서는 주소만 차지하고 연결을 WireGuard로 팜에 넘김, 디코이는 팜 안의 별도 VM
- VPC엔 L2가 없어 벤더 원본(L2 브리지) 대신 L3 → 새 단서: **TTL(홉 수)·MSS(터널 크기)**. 장애를 고친 방법(MSS 조정)이 새 단서가 되기도 함
- 컨테이너로 만들었더니 `systemd-detect-virt` = nspawn, auditd 불가 → **KVM VM**으로(Attivo가 팜 안에 VM을 두는 이유)
- [채울 것] 투영 구조 그림

### 3-6. "주변과 섞이게"는 "같은 이력"이었다
- 이름·주소는 규칙 몇 줄. 진짜 어려운 건 패치 수준 — 최신이 아니라 **이웃과 같은 날, 같은 순서**(이미지 → 자동 보안 업데이트 → 사람의 업그레이드)를 밟아야 설치된 커널 목록까지 같아짐
- 벤더가 블렌딩을 "AI"·"지속적 재학습"이라 부르는 이유가 보임

### 3-7. 디코이 장치가 운영 서버를 먹통으로 만들 뻔했다
- 중계용 라우팅 규칙을 바꾼 뒤 networkd 재시작(업데이트 때 생김) → 운영 서버가 자기 주소로 오는 패킷을 못 받음
- 깨달음: 운영 서버를 디코이로 쓰는 순간 **디코이 장애 = 운영 장애**. 기준이 "잘 속이나" 앞에 **"망가져도 운영은 멀쩡한가"**. 고객이 디셉션 도입을 망설이는 진짜 이유
