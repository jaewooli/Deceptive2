# 메인 목표

**AWS에 가상 회사 인프라를 만들고, 상용 디셉션 제품의 핵심 기능을 직접 구현한 뒤, 내부 침투 공격 시나리오로 탐지가 되는지 검증한다. (마감: 2026-12-04)**

**이 프로젝트에서 얻고 싶은 것: 주요 솔루션의 주요 기능을 직접 만들어 보면서, 벤더가 왜 그렇게 설계했는지(또는 왜 동의하지 않는지)를 깨닫는 것.** 기능마다 학습 질문을 들고 구현하고, 깨달음은 `docs/04-learning-log.md`에 그날 기록한다.

목표 직무: 원청 내부 보안팀의 클라우드 탐지 엔지니어링 — 이 프로젝트는 위협 시나리오 설계, 로그 파이프라인, 탐지 룰·상관분석, 오탐 튜닝, Detection-as-Code, AWS 클라우드 탐지 역량을 증명한다 (`docs/03-job-mapping.md`)

## 핵심 원칙
- 원청 관점: "우리 인프라에 침투한 공격자를 빨리, 적은 오탐으로 잡는다"
- 데이터 규모나 성능 비교보다 기능 구현과 실제 공격에 반응하는지 검증
- 보고서는 기능마다 벤더 설계 → 직접 해보니 → 막힌 점 → 깨달음 → 검증 결과
- 마감을 넘기면 기간을 늘리지 않고 범위를 줄인다

## 구현 기능
1. 실제 OS 디코이 + 디코이 투영(포트·배너) + 진정성 검증 세트(디코이가 실제 운영 서버와 구별되는지 측정: 사용 흔적·연결 흔적·감시 장치 노출·이야기 일관성)
2. 파일·메모리 미끼(더미 DB 리스너), AWS 장기 키 미끼(IAM 역할 전환 후 남은 `backup-legacy` 키)
3. 결과 기반 감시(P0: authorized_keys·ld.so.preload·cron.d)
4. 경보와 침투 체인 상관분석, 디코이 세션 명령 첨부
5. (여유 시) 탐지/차단 모드 분리, HASSH, LLM 경보 요약, 감시 P1

## 성공 기준 (근거는 `docs/plan-wbs.md` 5절)
- ATT&CK 커버리지 P0 표의 탐지 대상 단계 100% 경보
- 호스트 경보 60초 이내(1-10-60 규칙), AWS 키 5분 이내(CloudTrail 지연)
- 기준선 오탐 원인 분석 → 억제 후 오탐 작업 재실행 시 0건, 공격 탐지율 유지
- 디코이와 실제 운영 서버 사이의 구별 단서 보완 전후 수 보고, 감시 장치 노출 단서 0개
- 시나리오 1 경보가 하나의 침투 체인으로 묶임
- 기능 1~4마다 학습 로그 1건 이상
